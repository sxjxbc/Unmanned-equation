# 雷达融合版运行与验证

实现日期：2026-10-12。该版本新增独立入口，原运行入口仍可使用。当前完成源码和离线验证，尚未完成目标机 ROS/Python 2.7 构建、录包回放或实车验收。

## 已实现

- `src/acceleration_event/src/lidar_road.py`：无 ROS/NumPy 依赖的几何核心。共享方向拟合两侧边界；默认连续三个有效雷达帧确认起步参考；两排观测更新方向，单排更新偏移并用 IMU 补偿方向；单侧观测仅限最后双侧观测后的短时窗口。不会用重复消息增加初始化支持度。
- `src/acceleration_event/src/genzong_lidar.py`：直接订阅 `/clustered_points`，使用原外参转换并过滤本车回波。原始时间戳与运动历史插值对齐，拒绝无时间、过期、倒序和错误坐标系输入。历史锥桶地图和旧规划路径不进入横向控制。
- 复用 `genzong_realtime.py` 的前瞻距离计算、误差滤波、PD方法和CAN编码；不运行其旧构造函数、1 Hz状态选择或双目标混合链路。前瞻目标仍使用原局部目标 ±1 米限幅。
- 定位回调及时更新完整控制状态。GPS位置仅参与速度估计、纵向进度与输入有效性；横向中心位置直接来自雷达。短期运动预测使用速度和IMU航向，速度仍受GPS质量间接影响，并非完全无GPS系统。
- 固定赛道方向投影计算纵向进度，不累加横向摆动；起点在新控制器就绪时锁定，仍不等价于物理发车信号。沿用75米配置。地图必须在测试过程中保持同一原点。
- 终点/输入超时触发后持续发送原 `raw=2000` 停车编码，状态锁存到节点重启；不因路径或锥桶缺失跳过停车处理。实际制动效果仍由原VCU协议决定。
- `/control/lidar_status` 发布JSON诊断；`/control/lidar_candidate_steering` 发布候选转角。`log_dir` 下保存 `lidar_fusion_*.jsonl`。只有实车输出开启时才发布 `/control/steering` 并打开CAN socket。

## 配置和恢复原版本

原 `acceleration_event.launch` 和三个原业务脚本未改。新 `acceleration_lidar.launch` 逐项复制当前原控制配置，包括重复参数的最终有效值；自动测试对照原启动文件检查配置一致性。当前尾部有效值为 `max_steering=0.50`、`kp_lateral=0.60`、`kp_heading=0.20`，没有擅自换成较早的参数。

外参取自当前原建图配置：x=1.76618、y=-0.11304、Y符号=-1、安装偏航=0.5度。2D几何不使用z偏移。若以后修改车机外参，必须同步新控制器与建图节点；当前两个节点的参数各自独立。

复制保留但新逻辑不消费的旧参数包括地图锥桶置信度、旧局部/全局混合权重、旧局部斜率限值、fixed_speed。原始 PoseArray 没有置信度字段，新链路使用几何有效性；不再混合地图目标，也不以旧斜率上限拒绝真实偏航。fixed_speed本来也不等价于VCU实车限速。

新增算法参数使用 `fusion_` 前缀，与原控制配置分开：

| 参数 | 默认值 | 用途 |
|---|---|---|
| fusion_init_frames | 3 | 不重复的连续有效观测支持数 |
| fusion_angle_gate | 0.35 rad | 相对运动补偿后先验的方向一致性门限 |
| fusion_offset_gate | 0.5 m | 帧间中心偏移一致性门限 |
| fusion_fit_residual | 0.25 m | 双边界残差、单边身份判定门限 |
| fusion_pose_timeout | 0.5 s | 现有定位消息有效期 |
| fusion_imu_timeout | 0.15 s | 控制时IMU有效期及外推时间上限 |
| fusion_lidar_frame | velodyne | 输入坐标系，可兼容前置 `/` |
| fusion_log_enabled | true | JSONL文件记录；失败时保留话题诊断 |

雷达观测保留期和运动历史最大间断继续使用原控制器 `local_timeout=0.35` 秒。单侧观测不能刷新最后双侧观测的保留期。以上新增门限是首轮验证值，必须对照真实消息频率和延迟，不能视作实测标定值。

当前基线备份：`backups/acceleration_before_lidar_fusion_20261012_230430/acceleration_event`；同目录 `SHA256.csv` 记录备份校验值。切回原算法只需停掉新控制器并使用原启动入口；本次并未覆盖原业务脚本。构建配置增加mapping依赖和脚本安装规则，如需恢复整个包，使用备份另行恢复即可。

## 车机准备

在原 Ubuntu/ROS Melodic 环境中构建，不新增或升级系统依赖：

```bash
cd ~/nrt_ws
source /opt/ros/melodic/setup.bash
catkin_make -j2
source devel/setup.bash
rospack find acceleration_event
```

路径按实际工作区调整。新模块通过catkin安装；`genzong_realtime.py`仍作为原算法入口，也被新模块导入以复用PD/CAN。构建配置保证被导入模块在devel/install中是真实Python文件，避免导入catkin可执行包装器。

传感器仍按你们现有方式启动；新launch同原入口一样不负责启动雷达和IMU驱动。IMU继续按原协议读取 `orientation.z` 的角度值，不能直接换成标准四元数消息。

## 第一轮：影子验证，不输出车辆指令

尚未运行建图节点时：

```bash
roslaunch acceleration_event acceleration_lidar.launch
```

已经运行原建图/控制链路，需要新模块旁路观察时：

```bash
roslaunch acceleration_event acceleration_lidar.launch start_mapping:=false
```

默认 `tracking_mode=shadow`，即使额外把enable_vehicle_output设成true，影子模式仍不会打开CAN socket。影子模式不改变其他已经运行的控制器输出。

新launch默认启动原建图节点以获得 `/vehicle_pose`，原建图可视化行为保持不变，仍可能需要桌面环境。已有位姿发布者时用 `start_mapping:=false`；不要重复运行两个同名建图节点。

检查：

```bash
rostopic echo /control/lidar_status
rostopic hz /clustered_points
rostopic hz /imu_data
rostopic hz /vehicle_pose
```

先原地验证中心、偏左、偏右、小角度偏航。当前X前Y右约定下，车偏左应测出正的横向目标。行驶旁路验证时，查看target是否随实际偏差持续变化，而非只有起步时变化。

诊断关键字段：`started`、`input_reason`、`observation_stamp/age`、`pose_stamp`、`imu_stamp`、`pairs`、`estimate_kind`、`target`、`steering`、`progress`、`stop_reason`、`udp_sent`。`started=true`表示算法开始计算闭环，不代表影子模式向车辆发指令。

常见状态：

- `waiting_time_alignment`：观测时间未被IMU运动历史包围，等待后续样本；不会用最新状态冒充采集时刻。
- `geometry_rejected`：空观测、支持不足或几何不一致；短时保留最后有效观测，但不刷新其原始时间。
- `road_stale`：道路观测超过保留期；`pose_stale/imu_stale`：对应输入过期。
- `motion_gap`：运动历史发生断档；`clock_rewind`：ROS时间回退。
- `finish`：固定轴进度达到终点。停车一旦触发，重新收到数据也不会自动恢复行驶，需停止本次运行并重新初始化。

## 录包和回放

```bash
rosbag record -O lidar_fusion_check.bag /GPS_data /imu_data \
  /clustered_points /vehicle_pose /control/lidar_status \
  /control/lidar_candidate_steering /control/steering
```

回放使用独立ROS会话，不运行任何实车输出控制器。下面用记录的位姿作为既有纵向/速度输入，因此禁用新建图；不要同时回放诊断和候选输出话题：

```bash
rosparam set /use_sim_time true
roslaunch acceleration_event acceleration_lidar.launch start_mapping:=false
# 另一终端
rosbag play --clock lidar_fusion_check.bag --topics /imu_data /clustered_points /vehicle_pose
```

重放或倒带时重启节点以清除锁存状态。恢复在线测试前，停止回放并把 `/use_sim_time` 设为false。

## 验证后接入实车

停止旧直线/八字控制器，确保只有一个车辆指令发布者；按已有有效的VCU方式限制车速。通过影子对照和转向方向、停车编码验证后，新入口为：

```bash
roslaunch acceleration_event acceleration_lidar.launch \
  tracking_mode:=control enable_vehicle_output:=true
```

已有建图运行时追加 `start_mapping:=false`。这个命令是部署说明，本次没有执行。先低速检查偏差出现后目标、命令与车辆响应是否连续一致，再逐级提速。

### 自检修复记录

1. 原驱动先发IMU再发GPS，建图位姿时间进一步晚于IMU。此前只查最新位姿对应的运动历史，可能一直无法完成启动。现保留位姿历史，选择最新且仍有效、能够被IMU历史插值覆盖的样本完成初始化。
2. CAN发送失败此前只写日志。现锁存 `can_send_failed`，立即尝试原停车编码，后续控制周期持续重试停车；发送成功本身仍不是VCU制动确认。
3. 关闭时设置关闭标志，屏蔽已经排队的控制回调，避免停止命令后再发送正常转向；重复关闭无副作用。
4. ROS Timer设置 `reset=True`，允许时间倒退后进入显式停车分支，而非定时线程先退出。测试验证构造参数及控制分支，实际ROS回放仍待验证。
5. 正式启动前若初始化参考过期，可重新进行多帧确认，避免卡死在旧参考；已启动后的故障锁存行为不变。

本轮新增测试先复现启动时序、发送失败和关闭后回调三项失败，修复后回归通过。再次对照备份哈希确认原三个业务脚本和原启动文件未变；配置一致性测试继续通过。

节点测试使用ROS传输替身，不是ROS集成测试；NumPy导入使用替身，但被复用的PD/CAN方法不调用NumPy。几何模块不依赖NumPy。代码按Python 2.7语法编写，本机没有Python 2.7/ROS/catkin，未验证目标运行时兼容性；原有依赖历史实现的其他测试未作为本次通过依据。
