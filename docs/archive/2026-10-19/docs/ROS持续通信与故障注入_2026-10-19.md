# ROS持续通信、故障注入与摆动排查

本轮在car虚拟机 `/home/car/nrt_validation_20261019` 的Ubuntu18.04/ROS Melodic/Python2.7环境中执行。各场景使用独立本地ROS master，车辆输出与显示关闭。没有真实传感器、CAN/VCU或车辆操作；结束后测试进程均已清理。

## 七项真实ROS检查全部通过

| 场景 | 观察结果 |
|---|---|
| 正常静止输入连续运行20秒 | 候选控制约20.01Hz，403条候选输出，未误停车；路径和道路状态持续更新 |
| 启动前4秒不发GPS，随后恢复 | 先等待，恢复后进入running，未锁死 |
| 雷达锥桶空帧0.2秒后恢复 | 未锁存停车，持续控制 |
| 雷达锥桶持续空帧1.4秒 | 约1.00秒后road_stale；恢复后仍保持stopped |
| 停止GPS发布1.4秒 | 约0.80秒后pose_stale；恢复后仍保持stopped |
| 停止IMU发布1.4秒 | 约0.80秒后imu_stale；恢复后仍保持stopped |
| IMU继续发布但时间戳滞后2秒 | 注入后约0.05秒识别imu_stale，保持停车锁存 |

停车场景检查候选转角归零，并观察到恢复后的锁存状态。各场景 `enabled=false`；ROS图均无 `/control/steering`、`/fssim/cmd`。这里的归零是候选输出状态，不是实车停止效果。

完整证据在 `exports/ros_fault_validation_20261019/guest_results/`：总报告、每场景result、逐消息状态和候选输出、注入时间、节点/master日志以及控制CSV。宿主回归测试仍为81项通过，保存在该目录旁的regressions子目录。

## 新增工具

`src/acceleration_event/scripts/ros_fault_validation.py`：Python2/3兼容的真实ROS测试编排。各场景启动自己的master、业务节点与合成传感器probe，保存结果并清理进程；没有引用或启用实车输出入口。

虚拟机中重新运行时必须指定新的结果目录，因为已有场景目录不会覆盖：

```bash
source /opt/ros/melodic/setup.bash
source ~/nrt_validation_20261019/devel/setup.bash
cd ~/nrt_validation_20261019
python src/acceleration_event/scripts/ros_fault_validation.py --output ~/nrt_ros_fault_repeat
```

`--cases normal short_road_gap`可仅执行指定场景。测试输入为静止合成数据，不能与真实传感器混在同一master中运行。

## 摆动原因的进一步证据

本轮没有修改生产PID、滤波、转角步长、前视或保护参数，仅为离线Harness新增独立参数覆盖，且始终强制关闭输出。

新增 `scripts/analyze_loop_response.py`，使用实际完整规划/控制循环，对同一个“偏移0.6米＋向外偏航10度”做18组对照：保持原配置、取消/减轻误差滤波、加快指令变化、仅使用全局目标，以及组合改变。结果在 `exports/loop_response_20261019/`。

例如，在**未标定**的轴距1.6米、速度2m/s、软件角度倍率1、执行响应0.1秒假设下：

| 离线试验 | 最大中心偏移 | 转角受变化率限制的周期比例 |
|---|---:|---:|
| 原配置 | 4.25米 | 89.1% |
| 仅将每周期步长0.012改为0.024 | 0.79米 | 32.2% |
| 仅取消误差滤波 | 0.87米 | 80.3% |
| 仅将滤波系数改为0.4 | 2.92米 | 99.6% |

这支持滤波和转角变化限制共同产生滞后的解释；也说明仅“稍微调快滤波”不一定有效。这里不是建议直接改实车步长。

原0.12滤波在20Hz下约0.9秒达到阶跃变化的90%；原0.012rad/周期约等于0.24rad/秒，指令从+0.3rad反向到-0.3rad至少要约2.5秒，尚未包含真实执行器延迟。这段期间车辆仍继续运动，可能造成扩大摆动。

另做18组带0.15秒执行延迟/0.2秒响应的试算，覆盖1、2、4.1667m/s及0.25、0.5、1的转角倍率，结果在 `delayed_sweep.json`。离线候选（滤波0.4、步长0.024）改善了部分场景，但在2m/s的部分假设和4.1667m/s多组场景仍失败。因此没有把该候选写入实车默认参数，也没有声称动态问题已修复。

## 本轮进度与下一步边界

- 已完成：真实ROS持续通信、启动恢复和三类输入故障/过期时间戳的停车状态验证。
- 已推进：闭环摆动的对照定位，说明为什么单独调整某一参数不足以保证稳定。
- 尚未完成：经真实车辆轴距、转角倍率、延迟标定后的闭环稳定性与VCU停车验收。

用户目前不清楚轴距和软件角度到真实轮角关系。没有这些参数时，合理下一步是继续在离线候选上研究/验证速度与延迟的稳定范围，保留失败场景，不把任意模型参数当作实车值。即使ROS状态机全部通过，也不能保证车辆在原速度下稳定跑完。
