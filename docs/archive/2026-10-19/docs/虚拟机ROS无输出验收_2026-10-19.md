# car虚拟机ROS无输出启动验收

## 本次真实环境结果

通过SSH在已运行的car虚拟机完成，不是ROS替身测试：

- Ubuntu 18.04.6 LTS，x86_64；ROS Melodic/roslaunch 1.14.13。
- catkin使用 `/usr/bin/python2`，Python 2.7.17；NumPy 1.13.3，OpenCV 3.2.0。
- 独立工作区 `/home/car/nrt_validation_20261019`，只包含当前验证需要的mapping和acceleration_event两个包。原 `/home/car/nrt_ws` 未覆盖。
- 两包 `catkin_make -j2` 通过，自定义消息生成通过；ROS与项目helper及控制模块导入通过。
- 使用独立127.0.0.1测试master，启用合成静止输入，关闭车辆输出和显示。
- 建图、规划、控制三个真实节点均可rosnode ping，传感器测试节点正常。
- 控制状态从等待进入running，`started=true`、`enabled=false`、`stop_reason=null`。
- CSV保存31个有效前瞻控制周期和31个不同候选转角，证明不只是节点存活，实际控制计算持续执行。
- ROS图中没有 `/control/steering` 或 `/fssim/cmd`；控制器没有初始化CAN客户端。测试退出后所属节点与测试master已结束。

## 发现并修复的阻塞

1. mapping的CMake导出了不存在的mapping库和system_lib。去掉这些虚假声明，按消息包导出message_runtime、geometry_msgs等依赖，并在package.xml声明geometry_msgs。修改前文件保存在结果目录。
2. Windows传输的Python文件缺少Linux执行权限，且部分使用CRLF。新增 `acceleration_event/scripts/prepare_linux_sources.py`，在独立Linux副本中规范换行并赋可执行权限，再重新构建。本机原始传输归档仍保留。

共享设置虽指向 `D:\bh_work\nrt_ws`，本次虚拟机内并未挂载该目录。没有更改VMware设置或挂载配置，源码经SSH同步。因此宿主后续修改不会自动更新这个独立验证副本。

## 在虚拟机重复检查

```bash
source /opt/ros/melodic/setup.bash
cd ~/nrt_validation_20261019
source devel/setup.bash
python src/acceleration_event/scripts/smoke_ros_validation.py
```

成功会打印 `PASS: synthetic stationary startup reached running; vehicle command topics absent` 和该次日志路径。脚本自行启动独立ROS master并清理其进程；不需要手动另起roscore。

从Windows重新传输包后，先在Linux副本运行：

```bash
python src/acceleration_event/scripts/prepare_linux_sources.py
catkin_make -j2
source devel/setup.bash
```

不要在必须保持原始文件字节的挂载共享源上运行规范化脚本，应先复制到Linux工作区。

## 这次通过的边界

本次是两个业务包的真实构建与静止合成输入启动检查，不是整个雷达驱动工作区的构建，也没有验证真实感知、GPS运动质量、CAN/VCU、轮角、实车制动或动态回归。

此前离线组合偏差和高速延迟模型仍存在未通过场景，本次启动通过不能覆盖这些问题。后续可在此ROS环境进一步做持续通信、故障注入和闭环仿真；真实车辆执行效果仍需设备验证。
