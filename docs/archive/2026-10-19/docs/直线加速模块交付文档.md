## 1. 交付目的与范围

本模块面向无人赛车直线加速场景，接收 GPS、IMU 和雷达锥桶观测，完成车辆定位、锥桶地图更新、直线中心线估计、局部路径规划、路径跟踪及纵向终点判定。

本次交付覆盖 `src/acceleration_event` 中的建图、规划、控制、公共数据质量库、启动配置和验证脚本。`mapping` 自定义消息、`imu` 定位驱动及 `lidar_nodes` 感知模块属于运行依赖，应按兼容版本同步部署。八字绕环模块不在本次功能验收范围内。

当前版本具备源码实现及离线验证入口，尚不能据此认定实车运行、停车能力或比赛要求已通过验收。摄像头融合、停稳反馈和 AS Finished 状态闭环尚未完成。

## 3. 环境与外部依赖

已记录的车机基线为 Ubuntu 18.04.6 LTS、ROS Melodic、Python 2.7.17、NumPy 1.13.3、OpenCV 3.2.0。该基线来自环境记录文件，接收方需在目标机重新检查。

运行依赖包括 ROS 的 rospy、tf、sensor_msgs、geometry_msgs、nav_msgs、std_msgs，以及 `mapping` 生成的消息。定位驱动依赖串口与设备权限；雷达链路依赖 Velodyne 驱动、地面分割和相应 Python 数值库，当前聚类实现使用 SciPy。

当前 INS 驱动以 `Imu.orientation.z` 承载航向角度数，不能直接按标准四元数解释。上游雷达坐标与车辆/地图坐标的 Y 轴约定不同，外参与轴向转换必须一起核对。

## 4. 系统流程与接口

```text
GPS + IMU + 雷达锥桶
          ↓
jiantu.py → /vehicle_pose + /cone_map
          ↓
zhixian_realtime.py → /planned_path + /planning/status
          ↓
genzong_realtime.py → 输入状态、CSV、使能后的车辆控制输出
```

| 话题 | 消息类型 | 说明 |
|---|---|---|
| `/GPS_data` | sensor_msgs/NavSatFix | 定位输入，要求有效状态、时间戳及质量信息 |
| `/imu_data` | sensor_msgs/Imu | 当前项目约定 orientation.z 为航向角度数 |
| `/lidar/cones` | mapping/ConeArray | 默认质量入口，雷达系坐标、原始观测时间、检测置信度 |
| `/clustered_points` | geometry_msgs/PoseArray | legacy 兼容入口，需显式选择，缺少检测置信度 |
| `/vehicle_pose` | geometry_msgs/PoseStamped | 地图系车辆位姿 |
| `/cone_map` | mapping/ConeArray | 提供给规划器的地图系锥桶观测 |
| `/planned_path` | nav_msgs/Path | 控制器实际跟踪路径 |
| `/planning/status` | std_msgs/String | JSON 质量状态，含路径、定位、观测时间及中心线信息 |
| `/control/input_status` | std_msgs/String | 输入可用性与控制状态诊断 |
| `/control/steering` | std_msgs/Float64 | 车辆输出使能后发布的转向命令 |

规划与控制必须同时部署。控制器要求路径与状态时间戳匹配，并检查原始观测年龄；重发路径不能延长旧观测的有效期。旧版缺少所需质量字段的状态不能直接作为新版控制输入。

## 5. 已实现行为

### 5.1 定位、初始化及建图

默认要求 GPS 状态为 0/1/2，水平协方差已知、有限、满足约束，水平对角方差均大于零且不超过 0.25 平方米。未知协方差默认拒绝。

车辆需静止完成初始化：有效 GPS 与对齐 IMU 连续覆盖 3 秒，至少 10 个样本，样本间隔不超过 0.5 秒；位置相对均值偏差不超过 0.30 米，航向偏差不超过 3 度。异常或不稳定观测重置初始化窗口。

雷达观测按检测时间与位姿历史对齐，单帧锥桶与已有地图对象按一对一关系关联，重复时间戳不增加独立帧支持。地图保留历史用于关联，规划输出使用当前帧更新的观测；有效空帧清空可用观测。

### 5.2 中心线规划与跟踪

规划器负责锥桶配对、质量评分和地图系中心线估计；启动需要完整左右配对。启动后可按历史线条件使用单侧观测兜底，单侧质量受到限制。局部路径前段使用渐变接入。

当前控制器只跟踪 `/planned_path`，不再混合另一条独立中心线目标。历史说明中关于直接中心线混合的描述属于旧实现；本文以当前源码和 launch 为准。CSV 中为兼容保留的 `centerline_blend_weight` 当前记为零。

零时间戳、过期输入、非有限值、重复或倒序位姿、位姿跳变、路径与质量状态不匹配等情况会抑制新的跟踪输出，并保留状态与日志。

### 5.3 终点判定与停车保持

纵向进度使用固定地图方向上的有符号投影：

`s = (x - start_x) × cos(finish_axis_yaw) + (y - start_y) × sin(finish_axis_yaw)`

横向摆动不会累计额外路程，倒退会减少进度。默认距离为 75 米；规划器的 `total_length=175.0` 是另一参数，不代表停车触发距离。

默认 `first_valid_pose` 在首次有效定位时锁定起点，不等同于物理发车信号。`configured` 模式使用指定地图坐标作为起点，地图重建后需要重新核对。

有效定位先更新终点状态，再检查路径与观测。达到终点后进入停车保持；车辆输出使能时持续发送当前协议中的 `raw=2000` 停车编码。输入随后失效也不会跳过已触发的停车分支。禁用车辆输出时不发送实际车辆指令。

## 6. 关键配置

| 参数 | 当前默认值 | 交接要求 |
|---|---|---|
| enable_vehicle_output | false | 联调初期保持关闭；实车输出需显式使能 |
| enable_visualization | true；验证入口 false | 无桌面环境使用 false |
| localization_mode | slam | 定位来源固定；仿真显式选择 fssim |
| cone_input_mode | quality | 质量链路默认用 /lidar/cones |
| sensor_timeout / pose_timeout | 0.5 秒 | 按真实频率、延迟和抖动校准 |
| alignment_tolerance | 0.15 秒 | 位姿与检测时间对齐容差 |
| path_timeout / path_observation_timeout | 0.5 秒 | 路径接收与原始观测有效期 |
| finish_distance | 75.0 米 | 赛道纵向终点触发值 |
| finish_start_mode | first_valid_pose | 明确首次定位与实际起跑线关系 |
| finish_axis_yaw | 0.0 弧度 | 地图 +X，需与赛道方向一致 |
| finish_confirm_samples | 1 | 终点确认样本数，需联调验证 |
| max_steering | 0.28 弧度 | 控制限幅，需车辆标定 |
| max_steering_step | 0.012 弧度/周期 | 舵角变化约束 |
| fixed_speed / max_vehicle_speed_mps | 4.1667 米/秒 | 控制配置值，不是实测限速能力证明 |
| can_dest_ip / can_dest_port | 192.168.0.7 / 20005 | 核对实际 CAN 网关 |
| can_self_port | 11312 | 本地端口，避免冲突 |
| lidar_offset_x/y/z | 1.76618 / -0.11304 / 0.42850 米 | 当前直线模块外参，必须独立测量确认 |
| lidar_y_sign / lidar_yaw_offset_deg | -1.0 / 0.5 度 | 核对坐标轴与安装朝向 |

直线模块与八字模块当前外参不同，不能直接互换。上游雷达现有入口默认为 270°、半径 5 米扇区；旧说明中的矩形裁剪和 30 米筛选范围不能作为当前 launch 的有效范围。

## 7. 部署与运行

以下命令在目标 Linux ROS 环境执行，假设源码已放入 `~/nrt_ws/src`。本次文档编制未执行这些命令。

### 7.1 环境检查与构建

```bash
source /opt/ros/melodic/setup.bash
cd ~/nrt_ws
bash src/acceleration_event/scripts/check_original_environment.sh
catkin_make -j2
source devel/setup.bash
rospack find acceleration_event
```

首次迁移需使用目标 Linux 环境对应的 catkin 顶层 CMake 配置，并确认第三方雷达包可被工作区发现。Windows 同步目录内的已有构建产物不能代替目标机重建。

旧部署记录曾因 mapping 导出不存在的库导致失败；当前 `mapping/CMakeLists.txt` 已不含该库导出，因此旧错误不能认定为当前仍存在。完整源码的最新目标机构建结果仍需补充。

### 7.2 在线输入验证：关闭车辆输出

另行启动经确认的 GPS/IMU 和雷达输入，在已 source 工作区的终端执行：

```bash
roslaunch acceleration_event acceleration_event.launch \
  enable_vehicle_output:=false enable_visualization:=false \
  log_dir:=$HOME/nrt_logs/acceleration_validation
```

检查三个业务节点是否存活，定位能否初始化，观测与路径质量是否有效。默认串口驱动发布 NO_FIX 和 UNKNOWN 协方差，严格链路无法据此完成初始化；需要接入真实定位质量来源。

仅兼容旧数据时，驱动可显式设置 `assume_gps_fix:=true`，建图可设置 `gps_allow_unknown_covariance:=true`。这两个开关分别作用于驱动和模块，不能替代真实质量验证；后者也不会放行 NO_FIX 或超限的已知协方差。

### 7.3 录包回放

```bash
roslaunch acceleration_event validation.launch \
  log_dir:=$HOME/nrt_logs/acceleration_replay
```

另一终端仅回放原始输入话题：

```bash
rosbag play --clock input.bag --topics /GPS_data /imu_data /lidar/cones
```

`input.bag` 替换为实际录包路径。旧 PoseArray 录包需在验证启动时加 `cone_input_mode:=legacy`，并将回放话题改为 `/clustered_points`。避免同时回放历史 `/vehicle_pose`、`/cone_map`、规划及控制输出。验证入口默认使用仿真时间，ROS 时间倒退后需重新初始化节点。

### 7.4 实车输出

完成接口、外参、急停、停车编码和失联行为验收后，可在常规启动入口显式设置 `enable_vehicle_output:=true`。直线与八字控制器不能同时占用本车控制链路。本文不将启动参数作为车辆已具备停稳保障的证明。

## 9. 已知限制与接收方待办

1. **定位质量来源尚缺。** 当前驱动没有可信质量字段协议，默认保守拒绝链路不能直接投入严格模式运行。
2. **故障停车闭环未完成。** 输入无效会抑制新跟踪输出，但停止发送不等于车辆停车；VCU 看门狗、制动反馈和独立 RES 需车辆侧确认。
3. **停车编码需联调确认。** 当前直线模块使用 raw=2000，两个赛事控制协议存在差异，不应未经确认跨模块复用。
4. **标定尚待完成。** 外参、GPS 噪声、初始化和超时阈值、配对门限、转向方向及控制参数均需实测。
5. **感知置信度为启发式评分。** 尺寸筛选不等于完整锥桶语义识别，地图关联门限也可能抑制距离较近的真实不同锥桶。
6. **版本资料需统一。** 旧分析报告及 DATA_QUALITY.md 部分历史描述与当前实现不同，需以源码、当前配置和新验收证据为准。

建议验收顺序为：版本归档 → 原环境构建 → 无输出在线检查 → 录包回放 → 车辆接口台架验证 → 受控低速测试 → 正式场景验收。

## 10. 常见问题与调试方法

### 10.1 调试顺序与数据留存

按“环境与节点 → 原始输入 → 定位 → 锥桶地图 → 规划 → 控制门控 → 车辆接口”的顺序排查，找到最先异常的一层后再向下检查。软件调试使用 `enable_vehicle_output:=false`，先用同一份录包复现；车辆台架和行驶调试按第 7.4 节完成前置确认。

以下命令在已 source ROS 和当前工作区的 Linux 终端执行。在线传感器验证使用真实 ROS 时间；录包验证使用 `validation.launch` 与 `rosbag play --clock`。

```bash
rosnode list
rosnode info /fsae_slam_node
rosnode info /straight_line_planner_realtime
rosnode info /path_tracking_controller
rosparam get /use_sim_time
rostopic echo -n 1 /planning/status
rostopic echo -n 1 /control/input_status
```

保留原始输入和诊断话题，便于复现同一时刻的链路状态：

```bash
mkdir -p "$HOME/nrt_logs"
rosparam dump "$HOME/nrt_logs/acceleration_params.yaml"
rosbag record -O "$HOME/nrt_logs/acceleration_debug.bag" \
  /GPS_data /imu_data /lidar/cones /vehicle_pose /cone_map \
  /planned_path /planning/status /control/input_status
```

legacy 模式额外录制 `/clustered_points`。录包按 Ctrl+C 正常结束，保留控制 CSV 和同次 ROS 日志。诊断包可包含中间输出，但重跑算法时仍只回放原始输入，避免新旧发布者同时写同一话题。

### 10.2 故障排查表

| 现象或日志 | 可能原因 | 检查及处理方法 |
|---|---|---|
| 找不到包、节点或 mapping 消息 | 未 source 正确工作区；消息未生成；脚本权限或解释器不匹配 | 执行 `rospack find acceleration_event`、`rospack find mapping`；检查构建的首个错误及 Python2 导入；重建后 source 同一工作区 |
| 构建脚本报告 baseline mismatch | 内核、系统包或 Python 库与记录基线不同 | 对照 `environment_baseline.json` 保存实际版本；此报错表示基线不一致，不一定代表功能不兼容；评估差异后单独验证，不能直接删除断言并宣称通过 |
| 节点启动后退出或 OpenCV 报错 | 依赖缺失；无显示环境；日志目录不可写 | 查看启动终端和 ROS 日志；设 `enable_visualization:=false`；检查真实 Python 环境和目录权限 |
| 原始 GPS/IMU 话题没有消息 | 驱动未启动；串口名称、权限或波特率错误 | 先查 `rostopic info` 的发布者，再查驱动日志、`/dev/imu` 链接与串口权限；不要在下游规划器调整参数掩盖输入缺失 |
| `GPS rejected: stale, no fix or invalid covariance/coordinates` | NO_FIX、未知或不合格协方差；经纬度超范围；时间戳过期 | 查看 NavSatFix 状态、协方差类型和值、经纬度及时间戳；默认串口驱动需要真实质量来源；旧数据兼容开关按第 7.2 节使用 |
| GPS/IMU 有消息，但始终没有车辆位姿 | 初始化窗口持续重置；车辆移动；频率低或航向抖动；IMU 无法对齐 | 静止采集，核对连续 3 秒/10 样本条件及间隔、位置和航向波动；检查日志是否出现 `[Init] Stable origin` |
| `Lidar cones rejected: unexpected frame` | 检测 frame_id 不符合建图入口约定 | 核对检测 header 与发布者，确认实际雷达系坐标；修正上游契约或经过核实的转换，不能只改 frame_id 标签而不转换坐标 |
| `Lidar frame rejected: no time-aligned pose` | 雷达与定位时钟不同；观测晚到；位姿缓存无覆盖；定位本身无效 | 对比检测时间与位姿时间范围；先修正时钟和时间戳来源，再测量延迟是否超过 0.15 秒容差 |
| 有点云，但 `/lidar/cones` 为空 | 无障碍物输出；锥桶点数、尺寸或置信度未过筛；超出裁剪区域 | 依次查看原始、预过滤、非地面点云及检测；确认 270°/5 米范围、地面高度和遮挡；用原始点云回放评估筛选门限 |
| 雷达有锥桶，但 `/cone_map` 少或为空 | 质量入口选错；位姿无效；检测时间/坐标错误；首帧支持偏低；关联抑制 | 核对 `cone_input_mode`、建图订阅者、定位及检测时间；对比检测置信度与地图置信度；检查是否反复使用同一时间戳 |
| `/planning/status` 的 reason 为 `pose_invalid` | 规划器没有可用或新鲜的位姿 | 回到 `/vehicle_pose` 层检查时间、频率和异常跳变，先恢复定位 |
| `/planning/status` 的 reason 为 `observation_invalid` | 观测为空或过期；配对/中心线不满足条件 | 查看地图中是否有完整左右对、置信度与原始观测时间；核对宽度 2.3～3.7 米、纵向差及车辆到中心线距离等门限 |
| 路径偶尔存在，但控制 reason 为 `path_or_observation_stale` | 路径与状态不同步；状态 valid 为 false；观测过期；旧版本字段缺失 | 同时检查 Path 时间戳、status 的 path_stamp、centerline 字段和 observation_stamp；确认唯一发布者及版本配套 |
| 没有 `/control/steering` 或 UDP 输出 | 输出开关关闭，这是验证模式的预期行为；也可能输入被抑制 | 先查输出使能参数及 `/control/input_status`；验证阶段不以“没有命令”为故障判据 |
| reason 为 `valid`，但车辆无响应 | 输出未使能；UDP 初始化失败；网关地址/端口、网络、CAN 协议或 VCU 状态不匹配 | 先确认输出门控，再在台架检查 socket、网络和网关接收；UDP 成功不等于 VCU 已执行 |
| 左右镜像、中心线整体偏移、转向方向相反 | Y 轴符号、雷达外参、航向单位或 steering_sign 错误 | 先用静态已知左右锥桶核对雷达→车辆→地图变换，再验证转向执行器方向；不能用 PD 增益补偿坐标错误 |
| 转向振荡或持续达到限幅 | 感知跳变、定位抖动、路径不连续、控制增益/前瞻不匹配 | 先看路径和误差是否平滑，再分析舵角及前瞻日志；一次只改变一个参数，用相同录包比较 |
| 未到终点就停车，或超过终点仍不触发 | 起点锁定时机或地图轴不正确；定位失效；确认样本不足 | 查看 finish_reference_x/y、finish_axis_yaw、finish_progress 和 finish_confirm_count；核对启动时位置与物理起跑线，不按累计轨迹长度解释进度 |
| reason 为 `normal_stop_latched`，车辆仍未停稳 | 终点已触发，但停车帧未发送/未被执行，或制动能力不足 | 对照网关与 VCU 帧记录、车辆速度和制动反馈；使用独立车辆中止途径处理，不能把该软件状态作为停稳反馈 |
| CSV 缺失、磁盘占满或运行变慢 | 日志路径不可写；/tmp 文件丢失；高频写盘带来 I/O 抖动 | 查看启动日志、`df -h` 及实际 log_dir；改用可写持久目录；同时对比处理耗时和输入延迟 |

### 10.3 定位、时间与感知的具体检查

```bash
rostopic info /GPS_data
rostopic hz /GPS_data
rostopic echo -n 1 /GPS_data
rostopic hz /imu_data
rostopic echo -n 1 /imu_data
rostopic echo -n 1 /vehicle_pose
rostopic echo -n 1 /lidar/cones
rosparam get /fsae_slam_node/cone_input_mode
```

`rostopic hz` 只反映收到消息的频率，不能证明采样时间正确或观测新鲜。核对 `header.stamp` 与当前 ROS 时间、录包时间范围和实际设备时间来源。回放时检查 `/clock` 是否推进；在线运行若启用 use_sim_time 而没有时钟，节点可能一直等待。

GPS 检查要同时看 `status.status`、`position_covariance_type` 与协方差，不只看经纬度。IMU 此处采用项目航向约定，不能套用标准四元数解释。检测时间戳应保持原始观测时刻，不能通过改成当前时间使旧观测看起来有效。

点云问题可在 RViz 中分别添加 `/velodyne_points`、`/prefiltered_points`、`/ground_segmentation/obstacle_cloud`，选取与消息 frame_id 一致且可显示的 Fixed Frame。用同一场景定位锥桶在哪一层消失，再检查高度、范围、聚类及质量门限。

### 10.4 规划与控制的具体检查

```bash
rostopic info /planned_path
rostopic info /planning/status
rostopic echo -n 1 /planned_path/header
rostopic echo -n 1 /planning/status
rostopic echo -n 1 /control/input_status
rosparam get /path_tracking_controller/enable_vehicle_output
rosparam get /path_tracking_controller/localization_mode
rosparam get /path_tracking_controller/log_dir
```

优先确认每个业务话题只有预期发布者。状态为 `valid` 后再查看 CSV 中的 `lookahead_found`、`lookahead_mode`、`lateral_error`、`heading_error`、`steering_angle` 和 `udp_sent`。当前 lookahead_mode 应为 `planned_path_only`；日志中的历史兼容字段不能当成仍有独立中心线混合的依据。

故障期间 CSV 可能只填写状态与终点字段，其他列为默认值。应结合 `input_reason` 和同一时刻的状态判断，不能把默认零误差当成正常跟踪结果。`udp_sent` 仅表示本地发送调用结果，不能证明网关接收、CAN 转发或执行器动作。

车辆接口台架检查可使用以下只读命令：

```bash
ip addr
ip route get 192.168.0.7
ss -lunp | grep 11312
```

结合网关接收日志或经授权的抓包核对目标 192.168.0.7:20005、CAN ID、字节序和停车编码。上述端口来自当前默认配置，修改参数后以运行时配置为准；不通过手工发送控制帧试探协议。

### 10.5 参数调试与问题闭环

先保存参数和基准录包，再调整一个参数组。定位与时间问题先修数据源；感知问题先看点云；几何问题先校准坐标与外参；输入和路径稳定后再调控制增益及前瞻距离。放宽超时、协方差或配对阈值可能掩盖坏输入，应记录依据并用包含正常、空帧、延迟、跳变、单侧和倒退场景的数据回归。

launch 中显式配置的参数会在下次启动时重新加载；源码中很多参数只在节点初始化时读取。不要假设运行期间 `rosparam set` 会立即改变节点行为。修改后在无车辆输出模式重启，并用 `rosparam get` 确认实际值。

每个问题记录：现象和发生时间、源码编号、参数快照、复现录包、最先异常的话题/状态、原因、修改项、前后对比及是否需要实车复验。关闭问题至少要有同场景复测和关联异常场景回归证据。
